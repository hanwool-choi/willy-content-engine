### 1.2 핵심 발견

1. **도달과 참여는 반대로 움직인다.** 조회수 1위(21만)의 참여율은 0.07%로 최하위권, 조회수 최하위 데일리룩(1.8천)의 참여율은 2.06%로 30배 높다. 세 포맷이 서로 다른 역할을 수행 중:
   - 이슈성 단품·세일 속보 → **신규 유입** 엔진
   - 족보 시리즈 → **팔로우 전환** 엔진
   - 데일리룩 → **코어 팬 리텐션**
2. **최고 도달 콘텐츠는 "패션"이 아니라 "신체 고민 해결"이었다.** (족저근막염 → 신발). 이 축의 글은 18건 중 1건뿐.
3. **시퀄은 급감한다.** `존버는 승리한다`(114) → `존버는 승리한다2`(16), 86% 하락. 훅 재사용은 빠르게 소모된다. 족보는 내용이 갱신되므로 유지된다.
4. **답글은 조건부 이벤트에서만 터진다.** 답글 71개는 무료나눔 1건뿐. 질문형 CTA는 3~5개에 그침.

### 1.3 이 프로젝트의 위치

`[내일 뭐입지?]`는 위 분류상 **데일리룩 = 코어 팬 리텐션** 포맷이다. 계정 내 도달 최하위(1.2~1.8천)이나 참여율은 최고(1.42~2.06%)이며, **매일 발행 가능한 유일한 포맷**이라는 점이 자산이다.

최종 목표는 협찬·광고 연계이며, 이를 위해 아이템 정보(제품명·가격·구매링크)를 함께 정리한다. 단 **메타데이터는 필수가 아닌 옵션**이다.

### 3.1 확정 수집 대상 (고정 URL)

```
https://www.musinsa.com/snap/main/today
https://www.uniqlo.com/kr/ko/stylingbook/stylehint/women
https://www.uniqlo.com/kr/ko/stylingbook/stylehint/men
```

### 3.2 검증에서 확인된 제약

- **세 페이지 모두 SPA다.** 유니클로는 6.8KB 셸만 오고, 무신사 스냅 초기 HTML의 이미지는 로고·기본 아이콘 2개뿐이다. → **Playwright 실브라우저가 필수**이며, 단순 HTTP 요청으로는 아무것도 얻지 못한다.
- **세 페이지 어디에도 기온·날씨 필터가 없다.** 무신사 스냅 내장 데이터 전수 검사 결과 `기온`/`온도`/`날씨`/`temperature` 모두 0건. → **"날씨에 맞춰 수집"은 불가능하며, "수집 후 날씨로 분류"로 순서가 뒤집힌다.**
- StyleHint 내부 API(`/v2/jp/outfit?ranking_manner=daily_ranking&option_location_country=South Korea&option_gender=…`)는 존재하나 토큰 헤더를 요구한다(`{"errorCode":403,"errorMessage":"token don't exits."}`). HTML 경로는 토큰 없이 접근 가능하다.

### 3.3 접근 원칙

- 수집은 **사용자가 버튼을 눌렀을 때만** 실행한다. 스케줄러 기반 자동 순회는 하지 않는다.
- CAPTCHA·봇 차단 우회는 구현하지 않는다.
- 수집 실패는 예외가 아닌 정상 분기로 처리한다(빈 결과 + 경고).

## 5. 컴포넌트 설계

각 컴포넌트는 독립 테스트 가능하며, 정의된 인터페이스로만 통신한다.

### 5.1 수집기 (`collector`)

**책임:** 고정 URL 3개 + 사용자 투입분에서 룩 이미지를 확보한다.

```
collect(sources: list[Source], limit_per_source: int) -> list[RawLook]

RawLook {
  look_id: str
  source: "musinsa_snap" | "uniqlo_women" | "uniqlo_men" | "manual"
  image_path: Path          # 원본 우선, 실패 시 캡처
  capture_method: "original_url" | "screenshot"
  source_url: str | None
  raw_meta: dict            # 제품명·브랜드 등, 있으면
  collected_at: datetime
}
```

**동작:**
- Playwright 브라우저 기동 (헤드리스 아님 — 사용자가 진행 상황을 볼 수 있음)
- 페이지별 렌더 완료 대기 후 룩 카드 추출
- 원본 이미지 URL 확보 시 원본 다운로드(고화질 우선), 실패 시 해당 영역 스크린샷으로 폴백
- 사용자 직접 투입: URL 붙여넣기 / 이미지 파일 드롭
- 제품명·브랜드가 DOM에 노출되면 `raw_meta`에 함께 저장 (옵션)

**수집량:** 소스당 기본 20개, 총 60개 목표. 14칸을 채우는 데 필요한 최소치의 4배 이상을 확보해야 기온 분포가 치우쳐도 배정이 가능하다. 분석 비용이 수집량에 비례하므로 설정으로 조정 가능하게 둔다.

**성별 판별:** 유니클로 URL 2개는 성별이 분리되어 있으나 무신사 스냅은 혼재한다. 따라서 `RawLook`에는 성별을 두지 않고, **분석기(5.2)가 판정한 `gender`를 유일한 기준으로 삼는다.** 유니클로 소스의 URL상 성별은 검증용 참고값으로만 쓴다.

**의존:** Playwright

### 5.2 룩 분석기 (`analyzer`)

**책임:** 이미지 1장을 기온 판정과 이미지 재생성에 모두 쓸 수 있는 구조로 변환한다.

```
analyze(raw_look: RawLook) -> LookAnalysis

LookAnalysis {
  look_id: str
  gender: "men" | "women"
  sleeve: "sleeveless" | "short" | "long"
  outer: str | None              # "shirt_jacket", "coat", …
  layers: int
  fabric_weight: "light" | "mid" | "heavy"
  coverage: "low" | "mid" | "high"
  temp_range: [int, int]         # 적정 기온 구간 (℃)
  rain_ok: bool
  season: "spring" | "summer" | "fall" | "winter"
  style_tags: list[str]
  palette: list[str]
}
```

**`season` 산출:** 비전 모델의 주관 판단이 아니라 `temp_range` 중앙값에서 규칙으로 파생한다 — `≥23℃: summer`, `17~22℃: spring/fall`, `<17℃: winter`. 봄·가을 구분은 수집 시점 월(3~5월=spring, 9~11월=fall)로 결정한다. 아카이브 폴백 조회의 일관성을 위해 결정론적으로 둔다.

**`rain_ok` 기준:** 우천 시 착용 가능 여부. 아우터 유무, 소재의 물 취약성(스웨이드·린넨 등), 하의 기장(바닥에 끌리는지)을 근거로 판정한다.

**설계 근거:** 메타데이터가 옵션이므로 제품 정보 없이 이미지만으로 기온 적합도를 산출해야 한다. `temp_range`는 배정에, `style_tags`·`palette`·`layers`는 재생성 프롬프트에 쓰인다. **분석 1회 → 두 곳에서 재사용.**

**의존:** Claude 비전 API

### 5.3 날씨 수집기 (`weather`)

**책임:** 서울 주간 7일 예보를 통일된 형태로 제공한다.

```
get_week_forecast(base_date: date) -> list[DayWeather]   # 7일

DayWeather {
  date: date
  weekday_ko: str                # "월" … "일"
  temp_min: int
  temp_max: int
  temp_repr: float               # (max × 0.6) + (min × 0.4)
  precip_prob: int               # %
  sky: str                       # "맑음" | "구름많음" | "흐림" | "비" | …
  resolution: "detailed" | "coarse"
}
```

**설계 근거 — API 2개를 이어붙여야 한다:**

| API | 커버 | 제공 항목 |
|---|---|---|
| 단기예보 `getVilageFcst` | 오늘 ~ +3일 | 3시간 단위 기온·강수확률·하늘상태 |
| 중기육상 `getMidLandFcst` + 중기기온 `getMidTa` | +3일 ~ +10일 | 오전/오후 강수확률, 일 최저/최고기온만 |

7일 커버를 위해 두 API를 병합하며, 뒷부분 4일은 해상도가 낮으므로 `resolution: "coarse"`로 표시한다. 서울 격자 좌표(nx, ny)는 상수로 고정한다.

**대안 검토:** OpenWeather One Call은 8일치가 한 번에 나와 단순하나, 한국 국지 예보 정확도가 낮다. 예보 오류가 곧 채널 신뢰도 손실이므로 기상청을 채택한다.

**의존:** 공공데이터포털 기상청 API 키

### 5.4 아카이브 (`archive`)

**책임:** 수집된 모든 룩을 인덱싱해 폴백 소스와 자산으로 축적한다.

```
save(look: LookAnalysis, image_path: Path) -> None
find_substitute(temp: float, rain_ok: bool, season: str,
                gender: str, exclude_recent_weeks: int = 4) -> LookAnalysis | None
```

**스키마 (SQLite):** `look_id`, `gender`, `temp_min`, `temp_max`, `rain_ok`, `season`, `style_tags`, `palette`, `image_path`, `source`, `collected_at`, `used_dates`

**설계 근거:** 비 예보일에 `rain_ok` 룩이 당일 수집분에 없을 수 있다. 아카이브가 있으면 과거분에서 대체할 수 있고, 운영이 쌓일수록 폴백 성공률이 오른다. `used_dates`로 4주 내 재등장을 차단한다.

### 5.5 배정기 (`assigner`)

**책임:** 룩 풀을 요일 7 × 성별 2 = 14칸에 최적 배정한다.

```
assign(looks: list[LookAnalysis], week: list[DayWeather])
    -> tuple[Assignment, list[Warning]]

Assignment: dict[(date, gender)] -> LookAnalysis | None
```

**비용 함수:**

```
cost(look, day) =
    abs(day.temp_repr - median(look.temp_range))
  + (day.precip_prob >= 60 and not look.rain_ok) ? 999 : 0
  + (day.temp_repr outside look.temp_range)      ? 5   : 0
```

**알고리즘:** `scipy.optimize.linear_sum_assignment` (헝가리안). 14칸 규모라 비용이 무시할 수준이며, 그리디는 앞 요일이 좋은 룩을 선점해 뒤 요일이 붕괴하는 문제가 있다.

**폴백 순서:**
1. 당일 수집분에서 배정
2. 실패 시 아카이브 조회 — 기온 ±3℃ AND `rain_ok` 일치 AND 같은 계절
3. 그래도 없으면 **빈 칸으로 남기고 경고**. 맞지 않는 룩을 억지로 배정하지 않는다

**경고 종류:** `EMPTY_SLOT`, `ARCHIVE_FALLBACK`, `RAIN_SUBSTITUTE`, `POOL_TOO_SMALL`(14개 미만)

### 5.6 이미지 재생성기 (`generator`)

**책임:** 원본 룩 이미지를 발행 가능한 이미지로 변환한다.

```
generate(source_image: Path, analysis: LookAnalysis,
         preset: ConceptPreset, strength: float) -> Path
```

**파이프라인:**

```
원본 캡처 → img2img (구도·핏 유지, 화풍 변환) → 모델 일관성 엔진 (고정 모델 적용) → 발행용
```

**설계 근거:** 무신사 스냅은 일반인 유저 사진, 유니클로 스타일링북은 직원 사진이다. img2img 단독으로는 실존 인물의 얼굴·체형이 결과물에 남는다. **모델 일관성 엔진이 고정 캐릭터로 인물을 덮어쓰는 것이 이 문제를 해소하는 핵심 단계**이므로 선택이 아닌 필수 단계로 둔다. `strength`(원본 유지 강도)는 엔진 확정 후 조정한다.

**엔진 추상화:** 생성 엔진이 미확정이므로 위 인터페이스만 고정하고 구현체는 교체 가능하게 둔다.

**컨셉 프리셋 (미확정 항목 격리):**

```yaml
# presets/concept_v1.yaml
concept_id: v1
model:
  men:   { age: "30대 초반", build: "보통", height: "175cm", hair: null, face_ref: null }
  women: { age: "30대 초반", build: "보통", height: "163cm", hair: null, face_ref: null }
render:
  art_style: null
  background: null
  lighting: null
  aspect_ratio: "4:5"
negative: ["손가락 왜곡", "텍스트", "로고"]
```

`null` 상태로도 파이프라인은 완성되며, 컨셉 확정 시 이 파일만 채우면 된다. 프리셋을 복수로 두어 A/B 테스트가 가능하다.

### 5.7 산출기 (`publisher`)

**책임:** 컨펌된 배정을 폴더와 문서로 물리화한다.

```
publish(assignment: Assignment, week: list[DayWeather],
        output_root: Path) -> Path
```

**폴더 구조:**

```
outputs/
└── 2026-08_W1/
    ├── _주간요약.docx
    ├── 08-03_월_맑음_29-24℃/
    │   ├── men/
    │   │   ├── _ref_원본_발행금지.jpg
    │   │   ├── 발행용.png
    │   │   └── analysis.json
    │   ├── women/
    │   │   └── (동일)
    │   └── 아이템정보.docx
    ├── 08-04_화_비_26-22℃/
    └── … (7일)
```

**규칙:**
- 폴더명에 날짜·요일·날씨·최고/최저기온을 모두 포함해 폴더만 보고 판단 가능하게 한다
- 원본 파일명에 `_발행금지`를 명시해 오발행을 방지한다
- **주차 계산은 ISO 기준**(해당 주 목요일이 속한 달)으로 정의해 월 경계 모호성을 제거한다
- `아이템정보.docx`: 요일·날씨 헤더 + 남녀별 아이템 표(제품명·브랜드·가격·구매링크). 메타데이터가 없으면 칸을 비우되 파일은 생성한다

**의존:** `python-docx`

### 5.8 컨펌 UI (`web`)

**책임:** 폴더 생성 전 전체를 확인·수정·컨펌한다.

**화면 구성:**

```
① 이번주 날씨 스트립     7일 · 기온 · 강수확률
② 수집 풀               썸네일 그리드 · 출처 배지 · temp_range · rain_ok
③ 배정 보드             요일 7 × 성별 2 = 14칸, 드래그로 교체
④ 경고 배너             빈 칸 / 아카이브 폴백 / 비 대체 표시
⑤ [1차 컨펌] ─────────→ AI 재생성 실행
⑥ 생성 결과 확인        칸별 [재생성] 버튼
⑦ [최종 컨펌] ────────→ 폴더 · 문서 생성
```

**설계 근거 — 컨펌을 2단계로 나눈 이유:** AI 생성은 14장이라 비용이 발생한다. 배정이 틀린 상태로 생성하면 전량 폐기된다. 배정을 먼저 확정한 뒤 생성하면 낭비가 없으며, 원 요구사항("미리 확인 후 컨펌하면 폴더링")도 충족한다.

**상태:** 컨펌 전 산출물은 임시 영역에만 존재한다.

**의존:** FastAPI + 단일 페이지 프론트
